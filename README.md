2. **Регистрация студентов через фасад `PosApplicationFacade` (GoF Facade)**;
3. **Наглядная защита доменных инвариантов (DDD Invariants)** с перехватом кастомного `DomainError`:

4. **Выставление корректных оценок** студентам;
5. **Исправление оценки** (пересдача студента с 5.0 до 8.0 баллов);
6. **Динамический расчёт итогового балла** в `GradeCalculationService` (Domain Service) с использованием взвешенной стратегии `WeightedGradeStrategy` и декоратора регламентного округления `RoundingGradeDecorator`;
7. **Экспорт итоговой ведомости** в форматы **CSV** и **JSON** с помощью паттерна `BaseReportExporter` (GoF Template Method).

## 📖 Предметная область и Ubiquitous Language

В коде и архитектурных решениях строго соблюдается единый язык предметной области (Ubiquitous Language):

| Термин | Английский термин в коде | Роль в системе |
|--------|--------------------------|----------------|
| **Студент** | `Student` | Обучающийся на курсе, чьи успехи и знания подлежат преподавательской оценке. Обладает уникальным идентификатором `StudentId`. |
| **Критерий** | `Criterion` | Параметр оценивания в рубрикаторе: название, максимальный балл (`max_score > 0`) и вклад в итог (`weight ∈ (0, 1]`). |
| **Рубрикатор** | `Rubric` | Корневой агрегат курса, управляющий согласованным набором критериев и защищающий целостность схемы оценивания. |
| **Оценка** | `Evaluation` | Зафиксированный факт выставления студенту балла по конкретному критерию с датой и комментарием преподавателя. |
| **Итог** | `FinalGrade` (`TotalScore`) | Расчётный результат студента, динамически вычисляемый на основе его оценок и весов критериев рубрикатора. |
| **Ошибка домена** | `DomainError` | Исключение при попытке нарушить бизнес-правило предметной области. |

## 🗺️ Карта DDD: Сущности, Value Objects и инварианты

В модуле «ПОС» реализована **богатая доменная модель (Rich Domain Model)**. Анемичные DTO и «сервисы-проходники» категорически исключены: логика валидации и охрана состояния инкапсулированы внутри домена.

### Разделение на Entity и Value Object

| Класс в коде | Тип DDD | Почему выбран этот тип (Обоснование / Reasoning) | Пример из кода |
|--------------|---------|---------------------------------------------------|----------------|
| `Student` | **Entity** | Обладает непрерывным жизненным циклом и неизменной идентичностью (`StudentId`). Два студента-однофамильца с одинаковым именем в одной группе — это **разные** студенты. Изменение ФИО или перевод в другую группу не меняют сущность студента. Сравнение производится исключительно по `_id`. | `class Student:`<br>`def __init__(self, id, full_name, group):`<br>`    self._id = id ...`<br>`def __eq__(self, o): return self._id == o._id` |
| `Evaluation` | **Entity** | Оценка имеет уникальный ID (`EvaluationId`) и жизненный цикл (может быть выставлена, изменена при апелляции/пересдаче через `update_score`, дополнена комментарием `update_comment`). Сравнение — строго по `_id`. | `class Evaluation:`<br>`def update_score(self, new_score, max_score):`<br>`    new_score.validate_against_max(max_score)`<br>`    self._score = new_score` |
| `Rubric` | **Aggregate Root** | Корневая сущность-агрегат, определяющая границы транзакционной целостности для критериев курса. Не позволяет добавить критерий с дублирующимся ID или именем, контролирует суммарный вес. | `class Rubric:`<br>`def add_criterion(self, criterion):`<br>`    if any(c.id == criterion.id ...): raise DomainError(...)` |
| `Score` | **Value Object** | Оценка в баллах не имеет собственной идентичности; 8.5 баллов — это всегда 8.5 баллов. Неизменяем (`frozen=True`). Гарантирует неотрицательность (`value >= 0`). | `@dataclass(frozen=True)`<br>`class Score:`<br>`    value: float`<br>`    def __post_init__(self):`<br>`        if self.value < 0: raise DomainError(...)` |
| `Weight` | **Value Object** | Вес критерия. Характеризуется только значением в диапазоне `(0, 1]`. Неизменяем (`frozen=True`), сравнивается по значению. | `@dataclass(frozen=True)`<br>`class Weight:`<br>`    value: float`<br>`    def __post_init__(self):`<br>`        if not (0 < self.value <= 1): raise DomainError(...)` |
| `Criterion` | **Value Object** | Спецификация критерия (название, максимум, вес). В контексте рубрикатора критерий является неизменяемым описанием правила (`frozen=True`). При редактировании возвращается новый экземпляр через функциональный метод `update()`. | `@dataclass(frozen=True)`<br>`class Criterion:`<br>`    id: CriterionId`<br>`    name: str`<br>`    max_score: float`<br>`    weight: Weight` |
| `FinalGrade` | **Value Object** | Результат расчёта. Является моментальным неизменяемым снимком успеваемости студента. Не хранится статически, всегда вычисляется Domain Service. | `@dataclass(frozen=True)`<br>`class FinalGrade:`<br>`    total_score: float`<br>`    max_possible: float`<br>`    percentage: float` |
| `StudentId`, `CriterionId`, `EvaluationId` | **Value Object** | Типизированные идентификаторы (Strongly Typed IDs), защищающие от случайной подмены строковых идентификаторов разных сущностей. | `@dataclass(frozen=True)`<br>`class StudentId:`<br>`    value: str` |

### Охраняемые инварианты домена
1. **Диапазон оценки**: балл не может быть отрицательным (`Score.value >= 0`) и не может превышать максимум критерия (`score <= criterion.max_score`). При нарушении выбрасывается `DomainError`.
2. **Существование критерия**: оценку `Evaluation` невозможно создать по несуществующему `CriterionId`. Фабрика `EvaluationFactory` сверяет критерий с утверждённым рубрикатором.
3. **Единственность оценки**: студент не может иметь две разные оценки по одному критерию. Повторное оценивание отклоняется фабрикой; разрешено только контролируемое исправление через метод сущности `update_score`.
4. **Валидность весов**: вес критерия обязан лежать в интервале `(0, 1]`. Суммарный вес критериев в рубрикаторе валидируется билдером `RubricBuilder` на равенство `1.0`.
5. **Динамичность итога**: итоговый балл `FinalGrade` **никогда не вводится пользователем вручную** и не хранится как статическое число в сущности студента. Он всегда рассчитывается динамически в доменном сервисе `GradeCalculationService` на основе актуальных оценок и рубрикатора.

## 🏛️ Архитектура: Ports and Adapters (Hexagonal)

Приложение спроектировано по принципам **Чистой архитектуры / Ports & Adapters (Гексагональная архитектура)**:
- Внутренний слой (**Domain**) полностью изолирован от внешнего мира и не содержит никаких внешних зависимостей (ни фреймворков, ни JSON, ни консоли).
- Прикладной слой (**Application**) реализует конкретные сценарии использования (Use Cases) и фасад (`PosApplicationFacade`), завися только от домена.
- Внешний слой (**Infrastructure / Adapters**) содержит адаптеры хранилищ, экспортёры и консольный интерфейс (CLI).
- **Стрелка зависимостей направлена строго внутрь: `Infrastructure` ➔ `Application` ➔ `Domain`**.

## 🧩 Паттерны проектирования GoF

В проекте применены 5 ключевых паттернов Gang of Four (GoF), закрывающих реальные потребности доменной модели и архитектуры (без оверинжиниринга «ради галочки»):

| Группа паттернов | Паттерн | Где реализован в коде | Какую боль / задачу решает в проекте |
|------------------|---------|------------------------|--------------------------------------|
| **Порождающие** *(Creational)* | **Factory** (`EvaluationFactory`) | [`src/domain/factory.py`](src/domain/factory.py) | **Боль:** Создание сущности `Evaluation` требует одновременной проверки нескольких взаимосвязанных инвариантов (существование критерия в рубрикаторе, непревышение максимума балла, отсутствие дубля оценки для студента).<br>**Решение:** Фабрика инкапсулирует сложные проверки в едином месте и исключает создание неконсистентной оценки. |
| **Порождающие** *(Creational)* | **Builder** (`RubricBuilder`) | [`src/domain/factory.py`](src/domain/factory.py) | **Боль:** Рубрикатор курса состоит из множества критериев, каждый из которых имеет вес и максимум. Ручная сборка чревата дублированием критериев и ошибками в сумме весов.<br>**Решение:** Строитель предоставляет Fluent API для пошаговой сборки и валидирует равенство суммы весов `1.0` при вызове `build()`. |
| **Структурные** *(Structural)* | **Facade** (`PosApplicationFacade`) | [`src/application/facade.py`](src/application/facade.py) | **Боль:** Консольный UI не должен знать о десятках отдельных классов Use Cases и напрямую оперировать репозиториями, иначе возникнет сильная связность UI с бизнес-логикой.<br>**Решение:** Фасад предоставляет простой унифицированный интерфейс для всех операций модуля оценивания. |
| **Структурные** *(Structural)* | **Decorator** (`RoundingGradeDecorator`, `BonusCapGradeDecorator`) | [`src/domain/services.py`](src/domain/services.py) | **Боль:** Требования регламента оценивания (округление по правилам ВШЭ до 2 знаков, ограничение максимального балла при бонусах) не должны загрязнять базовую математику расчёта средних баллов.<br>**Решение:** Декораторы прозрачно оборачивают стратегию расчёта, модифицируя финальный балл без изменения самой стратегии. |
| **Поведенческие** *(Behavioral)* | **Strategy** (`IGradeCalculationStrategy`, `WeightedGradeStrategy`, `NormalizedGradeStrategy`) | [`src/domain/services.py`](src/domain/services.py) | **Боль:** На разных курсах или этапах оценивания могут требоваться различные алгоритмы подведения итогов (взвешенная сумма по весам критериев, нормализованный процент, простое среднее).<br>**Решение:** Алгоритм расчёта инкапсулирован в сменяемые стратегии, подставляемые в `GradeCalculationService` через DI. |
| **Поведенческие** *(Behavioral)* | **Template Method** (`BaseReportExporter` ➔ `CsvReportExporter`, `JsonReportExporter`) | [`src/infrastructure/export.py`](src/infrastructure/export.py) | **Боль:** Процесс экспорта ведомости (валидация путей, создание папок, сериализация, запись в файл в UTF-8) одинаков, различается только синтаксис формата (CSV vs JSON).<br>**Решение:** Базовый класс определяет неизменный скелет алгоритма в `export()`, а подклассы переопределяют единственный шаг `_serialize()`. |

## 💉 DI-контейнер и Composition Root

Файл [`src/container.py`](src/container.py) реализует паттерн **Composition Root** (корень компоновки):
- Собирает весь граф объектов на самом краю приложения при его запуске;
- Связывает абстрактные порты домена с конкретными инфраструктурными адаптерами;
- Позволяет легко переключать режим хранилища (`storage_mode='json'` для реальной работы или `'memory'` для тестов и демо);
- Гарантирует соблюдение принципа инверсии зависимостей (Dependency Inversion Principle — SOLID D).

Пример использования в коде:
```python
from src.container import Container

# Инициализация контейнера в нужном режиме
container = Container(storage_mode="json", data_dir="data")

# Получение фасада для взаимодействия
facade = container.facade
student = facade.add_student("Алексей Смирнов", "БПИ-22-1")
```

## 🤖 Роль искусственного интеллекта в решении

В соответствии с регламентом домашнего задания и политикой академической честности, распределение задач при реализации проекта выглядело следующим образом:

### 👤 Выполнено студентом самостоятельно:

1. **Архитектурный анализ и проектирование слоёв (DDD & Architecture)**:
   - Полный анализ предметной области, формулирование словаря Ubiquitous Language;
   - Проектирование слоёной архитектуры Ports & Adapters (Hexagonal Architecture) со строгим направлением зависимостей внутрь;
   - Выделение границ агрегата `Rubric` и осознанное разделение концепций на Entity (`Student`, `Evaluation`) и Value Objects (`Score`, `Weight`, `Criterion`, `FinalGrade`, типизированные ID) для предотвращения анемичной доменной модели;
   - Подбор и архитектурное обоснование применения паттернов GoF (Factory, Builder, Facade, Decorator, Strategy, Template Method), решающих конкретные боли предметной области.

2. **Автоматизированное тестирование, верификация и отладка**:
   - Разработка матрицы тест-кейсов и написание исчерпывающего набора из **81 теста** (модульные и интеграционные тесты);
   - Верификация всех доменных инвариантов и краевых условий (включая защиту от отрицательных баллов, дублей оценок, `NaN` и `±Inf`);
   - Проведение сквозного аудита проекта на соответствие всем требованиям и критериям ТЗ;
   - Отладка краевых случаев, ручное тестирование интерактивного CLI (`main.py`) и сквозного демонстрационного сценария (`--demo`).

---

### 🤖 Использовался ИИ (как инструмент для генерации кода):

* **Генерация исходного кода по спецификации студента**:
  - Генерация шаблонного кода по спроектированной студентом архитектуре (структура `@dataclass(frozen=True)` для Value Objects, скелеты Use Cases);
  - Инкапсуляция состояния сущностей с приватными атрибутами и свойствами для чтения;
  - Первичная кодогенерация адаптеров персистентности (JSON и In-Memory репозитории) и каркаса DI-контейнера.

> **Ответственность студента:** Вся кодовая база и архитектурные решения были критически проверены, протестированы, глубоко отрефакторены и доработаны автором лично. Студент полностью понимает внутреннее устройство программы и готов защитить каждое проектное решение.

## 📁 Структура проекта

```
KPO_HW2/
├── src/                               # Исходный код приложения
│   ├── domain/                        # ДОМЕННЫЙ СЛОЙ (чистая бизнес-логика)
│   │   ├── __init__.py                # Экспорт ключевых доменных сущностей
│   │   ├── value_objects.py           # Value Objects: Score, Weight, Criterion, FinalGrade, IDs, DomainError
│   │   ├── entities.py                # Entities & Aggregates: Student, Evaluation, Rubric
│   │   ├── factory.py                 # GoF Creational: EvaluationFactory, RubricBuilder
│   │   ├── services.py                # Domain Service: GradeCalculationService, GoF Strategy & Decorator
│   │   └── repositories.py            # Outbound Ports: IStudentRepository, ICriterionRepository, IEvaluationRepository
│   │
│   ├── application/                   # ПРИКЛАДНОЙ СЛОЙ (Use Cases & Facade)
│   │   ├── __init__.py
│   │   ├── use_cases.py               # Прецеденты использования (AddStudent, GradeStudent, GetFinalResult...)
│   │   └── facade.py                  # GoF Structural: PosApplicationFacade (единая точка входа)
│   │
│   ├── infrastructure/                # ИНФРАСТРУКТУРНЫЙ СЛОЙ (Adapters & CLI)
│   │   ├── __init__.py
│   │   ├── repositories.py            # Адаптеры репозиториев: InMemory* и JsonFile*
│   │   ├── export.py                  # GoF Behavioral: BaseReportExporter, CsvReportExporter, JsonReportExporter
│   │   └── demo.py                    # Сквозной демонстрационный сценарий (Demo Runner)
│   │
│   ├── container.py                   # DI-контейнер (Composition Root)
│   └── __init__.py
│
├── tests/                             # МОДУЛЬНЫЕ И ИНТЕГРАЦИОННЫЕ ТЕСТЫ (pytest)
│   ├── __init__.py
│   ├── test_domain.py                 # 49 тестов: VO инварианты, Entity, Rubric, Factory, Builder, Services
│   └── test_use_cases.py              # 26 тестов: сценарии Use Cases, экспортёры, интеграция с контейнером
│
├── data/                              # Директория с данными JSON и отчётами экспорта (создаётся автоматически)
├── main.py                            # Консольный интерфейс пользователя (CLI) и точка входа
├── requirements.txt                   # Зависимости проекта (pytest>=7.0)
└── README.md                          # Полная документация решения
```
